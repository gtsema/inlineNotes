**2. Is the PNG decoder correct, and does it bite?** Correct for this file. `pngParts` (`:242`) walks chunks from offset 8, concatenates all `IDAT`s and reads `IHDR`; `decodeMascotFrame` (`:278`) refuses anything but bit depth 8 / color type 6 (`:283-287`), refuses an inflated length other than `height * (width*4 + 1)` (`:289-293`), and implements all five filters correctly: None/Sub/Up use reconstructed neighbours, Average uses `(left + up) >> 1` on 0-255 values (no sign bug, since `left + up ≤ 510`), Paeth is the standard predictor, and any other filter byte throws by name. Writing masks with `& 0xff` (`:330`). `border-radius: 50%` is modelled as the inscribed circle (`clipRadius = min(w,h)/2`, center at `w/2, h/2`) measured to pixel centers (`x + 0.5`), which is the right model. It bites: a **re-encode** trips the SHA-256 + size pins (`:379`) and the IHDR/IDAT walk; a **crop or pad** trips the `IHDR` pins at `:384` (128×128, 8, 6); an **interlaced** re-encode trips the inflated-length guard (an Adam7 128×128 frame needs 22 144 raw bytes, not 65 664) — the interlace byte (`ihdr[12]`) is itself not pinned, but the hash pin covers it; the painted-pixel count `13_054` is a second fingerprint (`:514`). The bound `0 < outsidePainted < 1_000` is **not** the rule — it is a non-vacuity guard the brief itself asked for ("hundreds rather than tens of thousands"), and it also catches a decoder regression. The rule is `outsideOpaque === 0` at `alpha ≥ 200` (`:524`), and because the file is hash-pinned the exact counts behind the spec's prose numbers cannot drift without tripping `:379`.
