## Residual risks for `t1-06-entry-write-path`

1. **Corrupt records vs a whole-list write (PM open question 1, still unanswered).** `loadEntries` returns only decoded entries (`src/core/entry-store-read.ts:229`), so a naive `set(entryStorageKey(key), { version: 1, entries: result.entries })` silently deletes the `corruptCount` records the read refused to delete. Whichever way the PM rules, the write path needs a test that pins it.
2. **Read-modify-write is not atomic.** `loadEntries` reads `pages:v1` and later publishes a removal derived from that stale read (`:223-228`); two tabs running the content script can clobber each other's index, and the `t1-06` slot+index commit inherits the same race. `writeSlotThenIndex` fixes ordering, not atomicity.
3. **Writing over an unusable index.** A store whose index decoded to empty with `layout_version`/`index_malformed` (`src/core/page-index-store.ts:86,82`) makes a create publish an index containing only the new key, orphaning every other page's slot. The read path never rewrites the foreign blob; the write path will. That needs an explicit rule in `t1-06` (refuse, or migrate).
4. **Fallback key vs a merely-unreadable index.** On `storage_unavailable` the read falls back to `pageKeyFromUrl(url)` (`:205`); if `t1-06` creates a slot under that fallback key while the index was only unreadable, it forks the page `N5` exists to prevent.
5. **Stamp producer must satisfy the reader.** The injected clock must emit a stamp matching `ISO_UTC_TIMESTAMP_PATTERN` (`:45`) or `t1-06`'s own writes will decode as malformed; no test covers that round trip yet.
6. **`SlotIndexCommit.value` is `unknown`** (`src/core/page-index-store.ts:57`), so nothing guarantees the written slot is `{ version: 1, entries }`; the writer needs a core-side producer, otherwise the read guard has no counterpart.
7. **Cap scoping and normalization** (t1-04 residuals 2 and 4) remain open by design: `assertCreatable` must receive only the current page's list, and persisted `authorName`/`comment` must be the `normalized` values.
8. **Quota classification is message-marker based** (`src/core/storage-port.ts:60-62,74-83`), never confirmed against real Chrome wording; a wording change degrades to `unavailable` and loses the Russian quota message. The 256-character key cap itself is still a defensive project constraint, not a quoted Chrome guarantee.
9. Add `entry-store-write.ts` (or whatever `t1-06` names it) to `MODULES` in `tests/core-storage-port.spec.ts:141` and R6's regex fix.
