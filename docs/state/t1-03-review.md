## Non-blocking findings

1. **N1 — `src/core/slot-key.ts:22-27` (collision trade-off has no spec clause).** The accepted FNV-1a collision risk for two long page keys sharing a 200-escaped-character prefix is stated only in a code comment; the owning spec (`docs/specs/inline-comment-model.md:41`) states the truncation rule but not the accepted risk. Not blocking: the behavior follows from the specified rule, so no unspecified behavior was invented. Recommend one clause at the next spec edit.
2. **N2 — `src/core/slot-key.ts:39` + `src/core/storage-keys.ts:17` (`{1,208}` is not a universal invariant; 9+247 = 256 is at the cap).** A slot kept whole may be up to 247 characters, so the universal bound on `entryStorageKey` is `^notes:v1:[A-Za-z0-9_%-]{1,247}$` and the resulting key can be exactly 256 characters. The AC3' `{1,208}` regex holds for the two mandated test keys and for every truncated slot, and the test is scoped exactly as the AC says, so the AC is met; the AC wording is what is imprecise. Needs a PM wording ruling (general claim `{1,247}`; `{1,208}` only for the truncation branch) and, if headroom is wanted, a separate ruling on budget 246. The committed spec does **not** overclaim, so this is not a spec/code conflict.
3. **N3 — `src/core/page-index.ts:25` (`readonly string[]` vs AC4/spec `string[]`).** TS type is stricter than the AC wording; the stored JSON shape is identical (`docs/specs/inline-comment-model.md:42`). Reviewer position: accept the `readonly` form, no change requested.
4. **N4 — `src/core/slot-key.ts:100` (200-character cut can split a multi-byte `%XX` group).** For a page key with non-ASCII characters past the cut (e.g. `https://example.com/` + `ä`×200), the truncated slot ends mid-escape and `decodeURIComponent(slot)` throws `URIError`. No shipped code decodes a slot (grep confirms `decodeURIComponent` appears only in `tests/`), and the test that decodes a slot uses ASCII only (`tests/core-storage-keys.spec.ts:99-109`). Keep the invariant of `docs/specs/inline-comment-model.md:42` ("a slot is resolved through the index, never by decoding the key text") in `t1-04`.
5. **N5 — `docs/specs/inline-comment-model.md:42` + `src/core/page-index.ts:38-45` (index add/remove semantics under-specified, and `addToIndex` accepts any non-empty trimmed string).** AC4's append-if-absent/keep-order/drop rules live in code and tests but only partly in the spec; `addToIndex` does not require its argument to be a normalized `pageKey`, so a caller that inserts a raw URL forks one page into two index entries and weakens the "never forks" guarantee of spec `:43`. Not blocking here (no write path exists yet); it is an invariant `t1-04` must establish: write via `resolvePageKey(url, index) ?? pageKeyFromUrl(url)`, then `addToIndex`.

## Residual risks for the PM (to be owned by `t1-04-core-entry-store`)

- **`pages:v1` write policy** — when the index is written relative to the slot write (index-first leaves an orphan index entry on failure; slot-first leaves an orphan slot that lookup cannot find), and whether `version` is validated on read (`page-index.ts:38-45` currently propagates the stored `version` unchanged, so a future `version: 2` value passes through silently).
- **Compaction and orphans** — whether an index entry whose slot holds zero entries is removed via `removeFromIndex` or kept, and what happens to an orphan slot with no index entry. Any compaction must never reorder `pageKeys`, because ruling `A4` ("oldest variant") is defined by index order (`src/core/page-index.ts:73-82`, test `tests/core-page-index.spec.ts:106-115`).
- **Index growth is unbounded by any specified cap** — one storage key holding every page key (each up to ~250 characters); the 20-entry-per-`pageKey` cap does not bound it. A `pages:v1` value that outgrows the storage quota or the (unverified) value-size limit makes every note unreachable. Needs a limit or a sharded-index ruling.
- **Index loss makes truncated slots unreachable** — for a page key whose escaped form exceeds 247, entries survive under the slot but cannot be recovered without the index entry (`docs/specs/inline-comment-model.md:42`); a rebuild-on-miss cannot recover such a page key.
- **Platform constraints still unverified** — charset + 256 remain defensive constraints; engineer open question 1 says the line must reach `docs/retro.md` at the end of Stage 1. A load-unpacked smoke that stores a page key with an escaped form > 247 characters would be the first empirical check.
- **No `chrome://extensions` verification performed** — justified: no shipped code reads or writes `pages:v1` yet, so there is no new observable behavior. `t1-04` owes that verification, including the Russian failure strings from a constants module.
