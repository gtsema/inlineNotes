## Blocking findings

1. **`src/content/capture/selection-span.ts:73, 92, 96` via `trimStreamRange` at `:187-198` — the span trim indexes the stream by UTF-16 unit while its arguments are code-point offsets.** `streamOffsetOfBoundary` (`:145-176`) correctly returns `fragment.streamStart + codePoints`, but `trimStreamRange` then probes that number with `streamText.charAt(begin)` (`:192`) and `streamText.charAt(finish - 1)` (`:195`), i.e. a UTF-16 index. With one astral code point earlier in the same stream, `charAt(k)` returns the character at code point `k − 1`, so: (a) if the character before the selection is a space — the ordinary case of a word selection — the loop "trims" a separator that is not there and `raw.start` advances by one code point, so `buildAnchor(stream.text, raw.start, raw.end, …)` (`:92`) and `candidate` (`:96`) describe a span one code point short: selecting `hello world` on such a page stores `anchor.text = "ello world"` and a candidate one code point narrower; (b) for a one-word selection the shift can degenerate the range (`:79` `raw.end <= raw.start`) and `captureSpan` answers `null`, so no card opens at all, or `createNote` answers `selection_lost` at save time (`src/content/create/create-note.ts:115-118`); (c) the narrowed candidate also breaks the `duplicate` answer of ruling `A23` — the same re-selection is refused as `overlap` instead of `duplicate` (`src/core/entry-overlap.ts:154-175` compares ranges for equality). This violates `docs/specs/inline-comment-model.md` → Rules / Semantics → "Anchor domains" ("an anchor range and a fragment's stream offsets are code points … the two numbers are never interchangeable") and the module's own header (`:11-20`), and the doc-comment at `:180-186` asserts the opposite of the behaviour. Fix direction (not for me to choose): trim through the code-point maps already in scope — e.g. compare the code point at the boundary through `sliceCodePoints`/`Array.from` on the boundary fragment, or drop the separators by stepping over fragment-adjacent separator code points rather than by `charAt`. Required test: a capture fixture where an astral character precedes the selection (`tests/content-selection-capture.spec.ts:196` currently places the emoji **at** the selection, which is why 523 tests miss this) asserting `sliceCodePoints(stream.text, candidate.start, candidate.end) === anchor.text === '<the selected words>'`.
