## `t2-02` readiness

The DOM layer must feed `resolveAnchor`/`buildAnchor` **one and the same string**: `normalizeText(pageText)` built by walking the same subtree order it will map back to, with any block separators inserted **before** normalization and with the same separator count in both directions (`text-normalize.ts:50`; spec `:69`, `:71`). What it must map **back** is the half-open **code-point** range `[start, end)` returned by `anchor-resolve.ts:76`: convert with `utf16IndexAt(stream, start)` / `utf16IndexAt(stream, end)` (`text-normalize.ts:68`) and then to `(node, offset)` pairs; never mix `String.indexOf`/`Text.nodeValue` offsets into anchor ranges without `codePointOffsetAt` (`:86`). At capture time the offsets handed to `buildAnchor` must be offsets **of the trimmed span** — i.e. derive `text` as `normalizeText(sliceCodePoints(stream, start, end))` from that same stream and choose `start`/`end` so that `stream.includes(prefix + text + suffix)` holds (see remark R3): otherwise `entry-store-write.ts:191` refuses the create with `entry_invalid`, or the anchor silently loses its disambiguation power. Pass the real fragment count as `options.fragments` (stored as a hint only, spec `:68`). On `{ ok: false, code: 'anchor_not_found' }` paint nothing and keep the entry listed and deletable (spec `:73`); on a hit paint the **resolved** range, which may be shorter than the remembered selection. Re-resolve on load, bfcache and SPA URL change by rebuilding the stream — the core caches no position.

Residual risks for `t2-02-content-anchor-dom`:
1. The whole stream ⇄ DOM correspondence is untested until `t2-02` (`t1-06` residual 2 closed at string level only); `jsdom` enters there and must stay a devDependency, out of `dependencies`, `src/manifest.json` and `dist/` (`t1-06` residual 8).
2. Normalization ownership moved to the capture site (`A26`): a forgotten `normalizeText` on either side produces `entry_invalid` on create or a bare-text-only anchor, with no core signal (remarks R3, R5). The `chrome://extensions` load check is the only detector until a `t2-02` test exists.
3. A 40-code-point window on a page with an identical repeated sentence resolves to the first copy by document order (ruling `A24`); there is no UI signal for "anchored to a different copy", and the window is shortest exactly at the top of a long page (`anchor-build.ts:99-103`).
4. Re-resolve must be a pure rebuild: any cached position would break the stability property that `tests/core-anchor-resolve.spec.ts:114` pins.
5. Cross-tab race from `t1-05`/`t1-06` residual 4 is untouched: `loadPageContext` → `commitRecords` is still a read-modify-write window, and `t2-02` puts a second writer in the page.

Residual risks for `t2-03-core-overlap`:
1. Overlap comparison will be done on code-point ranges in one stream (half-open intervals), which matches the spec's "touching at one boundary is not an overlap" rule (`:67`), but only if every entry's anchor resolves; a stale anchor has no range, so the AC must say what happens when an existing entry is stale (currently unspecified).
2. `assertCreatable` receives only the current page's **decodable** list (`entry-store-write.ts:181-185`), hidden entries included (ruling `A22`); a resolved-range argument must be added without breaking the per-page cap test `tests/core-entry-store-write.spec.ts:238`.
3. The `A26` guard now sits between `assertCreatable` and the draft (`:191`); the overlap check belongs inside `assertCreatable` per spec `:34` order (name → selection → 256 → 20 → overlap → identical), so an added overlap rule must not reorder that sequence, and `tests/core-entry-store-write.spec.ts:875` must keep passing.
