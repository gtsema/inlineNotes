### Open questions

1. **Unhandled rejection / stuck-session risk (needs a PM ruling, not fixed here)**: `positionCard` → `firstFragmentBox` can *throw* (`range.setStart` out of bounds if the page mutates the selected text node during the 150 ms settle). `attachCreateCardEvents` calls `void controller.capture()`, so the rejection is unhandled and `session` stays set with no mounted card: `isOpen()` reports `true` and no card opens until a scroll/click closes it. Existing spec language only covers `positionCard` returning `null`. Proposed minimal fix: make `RangeForFragment` return `Range | null` (or wrap `capture()` in a try/catch calling `close()`), plus a spec line saying a measurement failure closes the card.
2. **jsdom gaps for `t3-02`**: `Range.prototype.getClientRects` and `getBoundingClientRect` do not exist in jsdom (they do in Chrome). My `events` tests therefore inject the `rangeFor` seam. The `t3-02` brief must either require a rects seam or forbid measuring assertions, otherwise its tests will fail for the wrong reason.
3. **`settle delay` value**: the spec names the term but keeps the number (150 ms) in code; only `SELECTION_SETTLE_MS > 0` is asserted. Should the number be durable in the spec?
4. **No browser run**: `chrome://extensions` load of `dist/` was not performed here (no Chrome in this environment); the observable-behavior list is verified in jsdom only.
