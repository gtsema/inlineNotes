# inline-comment-model

## Purpose / Goal

Define the stored object of the product: what a note is, where it lives, how it is keyed to a page, who may change it, and when it stops being displayable. This spec is the single owner of those rules; UI layers must not restate or relax them.

## Scope

In scope: entry shape, storage area and keys, page-key normalization, caps, authorship and edit rights, overlap rejection, anchoring and staleness, deletion and page clearing.
Out of scope: how the highlight is painted and how the popup is rendered (`content-overlay-ui.md`), MV3 permission wiring, any cross-device or cross-user sharing.

## Flow / Sequence

1. Content script captures a non-empty user selection and resolves it to an ordered list of `(element, startOffset, endOffset)` fragments. It also builds the normalized text stream of the page and the code-point range of the selection inside that stream, and hands core only normalized text (ruling `A26`).
2. Core computes `pageKey` from the current URL and loads `entries[pageKey]`.
3. Core checks the creation rules in this order: name set → selection not empty → comment length ≤ 256 → entry count < 20 → no overlap → no identical existing entry. The last two steps work on `resolved range` values from one re-resolve pass (ruling `A37`), never on stored anchor text, and report the machine codes `overlap` and `duplicate`; the Russian wording is mapped in the UI layer. Every shipped create hands core one `spans` argument — the candidate `resolved range` plus the resolved range of every existing entry of that page, all built from the same page read — and the write API requires it, so a create that resolved nothing fails to compile instead of silently skipping the last two checks (ruling `A46`). Steps 5 and 6 scan only the `own entry` half of the page list: the list is filtered by the `author identity` rule before the comparison (`A93`, `A99`), while step 4 counts every entry of the page whatever its author.
4. Core builds the entry: `id` (random 12-char base36), `pageKey`, `authorName`, `text` (normalized selection text), `comment`, `anchor`, `visible` (default `true`, PM ruling `A1`), `createdAt`, `updatedAt` (UTC ISO-8601 `Z` strings taken from the caller's injected clock, same value on create; ruling `A9`).
5. Core writes the whole page list under one storage key through the storage port, under the Index write policy below, and notifies the content script and popup. A refused or failed write changes nothing in the store and carries a machine code.
6. On page load or SPA URL change, the content script asks core for the page's entries, rebuilds the normalized text stream of the current subtree, resolves each anchor against that stream, and reports which entries are displayable; a displayable entry also gets its `text fragment` list, which is what the highlight is painted over.
7. Edit path: the editor may save only if `entry.authorName === currentName`; a save under another current name is refused with the `not_author` code. The save rewrites only `comment` (normalized) and `updatedAt`; `id`, `pageKey`, `authorName`, `text`, `anchor`, `visible` and `createdAt` keep their stored values.
8. Delete path: remove by `id` — that is the `Удалить` of the page card, and it stays exactly one entry. Delete-author path: remove every entry of one `authorName` of one page in **one** call, `deleteEntriesOfAuthor` (ruling `A108`) — that is the `Удалить` of a popup `author row`. Clear page: remove the whole `pageKey` list. Visibility path: one entry through `setVisible`, or every entry of one `author group` through `setVisibleForAuthor` (the popup checkbox, ruling `A108`).

## Rules / Semantics

- Storage: `chrome.storage.local` only. One key per page: `notes:v1:<slotKey>`, value `{ version: 1, entries: Entry[] }`. A separate key `settings:v1` holds `{ name }`; a separate key `pages:v1` holds the page index.
- Slot key encoding (`A7`): a storage key uses only characters legal for `chrome.storage` keys, so a raw `pageKey` (a whole URL) never appears in one. Every character outside `[A-Za-z0-9_-]` is replaced by its uppercase `%XX` UTF-8 escape, so the escaped alphabet is `[A-Za-z0-9_%-]` and `decodeURIComponent` of the escaped slot key returns the original `pageKey`.
- Slot key length (`A7`): an escaped slot key longer than 246 characters becomes its first 200 escaped characters + `~` + `fnv1a32(pageKey)` in base36 padded to 7 characters, so a truncated slot key is at most 208 characters, no slot key exceeds 246 characters, and `notes:v1:` (9 characters) + slot key is at most 255 characters: strictly inside the 256-character key budget, with headroom instead of none (review finding `N2`). `~` is legal as the separator because the escape never emits it (a `pageKey` carrying `~` produces `%7E`), so a page key cannot forge it. A truncated slot key is not reversible. Accepted trade-off (review finding `N1`): two page keys that share the first 200 escaped characters and collide in the 32-bit FNV-1a hash would share one slot; the hash covers the whole page key and the store holds a few dozen keys, so the risk is accepted, and the page index keeps both keys either way. The charset rule and the 256-character budget are defensive project constraints, not a quotation of a published Chrome statement (not confirmed empirically).
- Slot key decode invariant (`N4`): no shipped code turns a slot key back into a `pageKey`. The `pages:v1` index is the only way back to a page key; reversing the escape exists in tests only, because a truncated slot key cannot be reversed at all.
- Page index: `pages:v1` holds `{ version: 1, pageKeys: string[] }` in insertion order and is the authoritative source of page keys. A slot is resolved through the index, never by decoding the key text, because a truncated slot key cannot be decoded back to a `pageKey`. Nothing in the read path reorders `pageKeys`: insertion order is what "oldest variant" means for the fallback below (`A4`).
- Storage seam: `src/core/` owns the `StoragePort` contract — promise-based `get(keys | null)`, `set(items)`, `remove(keys)` — and calls no storage API itself. `chrome.storage.local` is reached through exactly one adapter in the content layer (`src/content/store/chrome-storage-port.ts`); unit tests use a hand-written in-memory port. A failed operation carries the machine code `quota`, `serialization` or `unavailable`; the Russian wording for a full quota is mapped in the UI layer.
- Settings record (`A31`, split out of `t4-02` by `A34`): `settings:v1` holds exactly `{ name }` and nothing else, where `name` is the value the author-name rule produced (trimmed, at most `MAX_AUTHOR_NAME_CODE_POINTS` code points). Exactly one core module reads and writes that key, and every UI half — the page card, the popup, the options page — goes through it, so the three layers can never disagree about who the current author is. Unknown fields left by another writer are ignored on read and are dropped by the next save. There is no settings delete in v1: nothing clears the key.
- Settings read (task `t3-01`): the core read returns `{ name, codes }` and throws nothing. An absent `settings:v1`, a value that is not an object, or an object whose `name` is not a string is `name: ''` plus `settings_malformed`; a port read that fails is `name: ''` plus `storage_unavailable`; a decodable `name` is returned normalized by `validateAuthorName` (trimmed) with no code. A name the author-name rule refuses — empty after the trim, or longer than `MAX_AUTHOR_NAME_CODE_POINTS` — carries `name_required`: ruling `A11` keeps that the single code for v1 (no `name_too_long`), because the options input refuses an over-long name before it can be stored. The read issues exactly one `get` of that key and no `set` and no `remove`: it normalizes and never rewrites, so a damaged, empty or over-long stored value survives the read verbatim and is repaired only by an explicit save. A caller asks "is there an author" by handing the returned `name` to `validateAuthorName`, never by re-decoding storage, and a name the rule refuses means the creation path is disabled, which is what keeps the card from opening (AC9).
- Settings write (task `t3-01`, UI half owned by `t4-02-options-name`): the core save writes the single key with the value `validateAuthorName(name).normalized` and nothing else, and returns that normalized name. A name the author-name rule refuses — empty, whitespace-only, or above the cap — is refused with `name_required` before any port call, so nothing is written. A port rejection is reported with the port's own code (`quota`, `serialization`, `unavailable`) and leaves the stored value byte-identical, because the name decides who may edit every existing entry and must never be half-saved. Saving a name is the only write that path performs, and a rename that deletes the previous name's notes performs the settings write **first** and the sweep second (ruling `A174`, "Rename sweep"): the sweep is a separate core call, so a failed name save leaves every note in place.
- Index write policy: a page slot is written **before** `pages:v1`, and a failed slot write leaves `pages:v1` exactly as it was. The index is published last, and what is published is the decoded `pages:v1` value that the read path produced, not a value rebuilt from the URL, so an index that lists a page always points at a slot that already landed. Removing the last entry of a page removes its slot **before** the index stops listing the page; a failed removal leaves the index untouched.
- Index write guard: a write derives its `pageKey` from the stored index and refuses rather than working around a bad index. `layout_version` or `index_malformed` in the stored value, or a failed index read (`storage_unavailable`), refuses create, save, delete, visibility and clear with that same code: publishing a one-key index would orphan every other page's slot, and the `pageKeyFromUrl` fallback would fork a page that already has entries under an indexed variant (review finding `N5`, residual risks 3 and 4 of `t1-05`). A missing `pages:v1` carries no code, so a first write is not refused. The same guard refuses a write over a slot value that is not a `{ version, entries }` object or whose `version` is not `1` (`slot_malformed`, `layout_version`); clear page is the one write allowed to drop such a value.
- Decode on write: every record a write publishes is produced by the read guard, so no write can store a record its own reader would skip; a create whose injected stamp or anchor is invalid is refused with `entry_invalid` instead of being stored. The stored `authorName` and `comment` are the normalized values, `id` comes from the injected random source, and both stamps come from the injected clock.
- Unreadable records (PM ruling `A16`): a stored record the read guard cannot decode survives every write verbatim — create, save, delete, visibility — and is dropped only by clear page, because that is an explicit user action. Caps count only the decodable records of the resolved page.
- Index read: a stored `pages:v1` whose `version` is not `1` is read as an empty index plus the `layout_version` code, never as a crash; a value that is not an index object is read the same way with the `index_malformed` code. A non-string element is dropped; an indexed key that is not normalized is kept, so the slot it already owns stays reachable.
- Index repair on read: a `pageKey` that `pages:v1` lists while its slot is absent or holds a well-formed empty list is dropped from the index with `removeFromIndex`, and every surviving key keeps its position. A slot that holds a malformed record, or a slot with a foreign `version`, keeps its index entry: dropping the key would make unreadable data unreachable, which is a silent delete.
- Decode on read: every stored record passes a guard in `src/core/` before it can reach `canEdit` or a list helper. A slot value that is not a `{ version, entries }` object is an empty page plus `slot_malformed`. Unknown fields are ignored, an absent `visible` means `true` (`A1`), and a malformed record is skipped and counted, never rewritten and never deleted. A record is malformed when an identity field is missing or empty, when a text field is not a string, when `anchor` is not `{ text, prefix, suffix, fragmentCount }` with a non-negative integer `fragmentCount`, or when `createdAt`/`updatedAt` is not a UTC ISO-8601 `Z` stamp.
- Page read result: the core read of one page returns `{ pageKey, entries, corruptCount, codes }` — the page key the read used (`null` when the URL is unparsable), the decoded entries in stored order, the number of records the guard skipped, and machine codes (`layout_version`, `index_malformed`, `page_key_invalid`, `page_key_unnormalized`, `slot_malformed`, `entry_malformed`, `storage_unavailable`, `url_unparsable`, `index_repaired`, `index_repair_failed`). Codes are machine-readable only; the Russian wording is mapped in the UI layer. A read never rewrites a slot and never deletes a record: its only permitted write is an index repair.
- Timestamps (`A9`): `createdAt` and `updatedAt` are UTC ISO-8601 strings with a literal `Z`, produced by a clock the caller injects; `src/core/` never reads a clock and never generates an id. Lexical order of those two fields is therefore chronological, which is what the popup ordering uses.
- Page lookup: an exact normalized `pageKey` match first; otherwise the oldest path-only match, meaning the earliest key in `pages:v1` whose `origin + pathname` equals the URL's (`A4`), and that fallback runs only when the index read succeeded (`index_ok` or an absent `pages:v1`); after `index_malformed`, `layout_version` or `storage_unavailable` there is no ordered index to search, so the write path uses the normalized URL alone (review finding `R3`). The stored key is used unchanged, so a page never forks into two entry lists. The write path resolves the key as `resolvePageKey(url, index) ?? pageKeyFromUrl(url)` and only then indexes it; `addToIndex` refuses a page key that `pageKeyFromUrl` did not produce, because indexing a raw URL would fork a page invisibly (review finding `N5`).
- No sync, no IndexedDB, no server. Nothing leaves the browser.
- `pageKey` normalization: `origin + pathname` in lowercase path; drop the hash; drop query params matching `utm_*`, `gclid`, `gsas`, `fbclid`, `_ga`, `_gl`, `_hs`, `mc_*`, `ref`, `ref_src`, `igshid`, `s_kwcid`; keep remaining params sorted by name. A trailing slash is not part of page identity: `/a`, `/a/` and `/a//` give the key of `/a`, while the site root keeps its own `/` key (`A8`); an `index.html` suffix is not normalized (reviewer note `R7`). Lookup additionally falls back to an `origin + pathname` (path-only) match against indexed keys, so a note saved on a URL that later gains or loses parameters is still found.
- Cap 256 characters counts Unicode code points of `comment`, trimmed of leading/trailing whitespace. Empty comment after trim → rejected.
- Cap 20 entries per `pageKey`. Creation at the cap is refused with the message `Достигнут лимит 20 записей на странице`.
- `authorName` is mandatory and must be a non-empty trimmed string, at most 40 Unicode code points (review remark `R2`; a surrogate pair counts once). If it is missing, creation and editing are disabled and the popup shows `Укажите имя в настройках`. First run generates a random 8-character name (lowercase base36) and stores it. The generation runs over **every** stored name the rule refuses — no record at all, a value that is not a record, a `name` that is not a string, empty after the trim, or over the cap — and never over a settings read that failed (`storage_unavailable`): the page writes no fresh identity into an area it could not read, because that identity would decide the edit rights of every stored entry. The UI half — field, counter, when the page opens, wording — is owned by `content-overlay-ui.md` -> "Options author-name field". The stored value itself is owned by "Settings record", "Settings read" and "Settings write" above; `t4-02-options-name` is the only shipped caller of the settings save and the only place the first-run generated name is wired, and no layer may hold a second reader of `settings:v1` or generate a name of its own.
- Identity is the name string itself, compared case-sensitively and after trimming. Two different names in the same browser are two different authors; there is no account concept. This one comparison decides every author question in the product — edit rights, the `own entry` label, and which entries the `overlap` and `duplicate` checks scan (`A99`) — and no layer may compare `authorName` a second way; an untrimmed or case-folded variant would answer the same pair of strings twice.
- Edit rights: only the author of the entry. A different current name gets no edit affordance on that entry; the entry is read-only. A `foreign entry` never blocks anything the reader creates: the overlap rule is per author (`A93`), so a note of the reader's own may be put on words another author already covered and both entries exist; how two coexisting highlights look is owned by `content-overlay-ui.md`, not here.
- Overlap: a new **or moved** range that intersects the `resolved range` of an `own entry` on the same page is refused with the message `Выделение пересекается с существующей записью`. The scoping is per author at **every** call site — the create gate and the editor's re-selection check alike (rulings `A93`, `A100`) — and the range of a `foreign entry` intersects nothing for this rule. Touching at a single boundary point is not an overlap. A moved range is the editor path (`t3-03` in `content-overlay-ui.md`): a re-selection there goes through this same check, with the entry being edited excluded from the entry list the check scans so an entry never collides with itself, and with the same per-author filter applied to that list (`A100`).
- Resolved range (ruling `A37`): "the range of an entry" in the overlap and duplicate rules is the half-open code-point range `[start, end)` that the entry's anchor resolves to **on the current normalized text stream** — never the stored `anchor.text`, never a stored DOM offset. One re-resolve pass supplies the candidate range plus the range of every existing entry of that page **the decision scans** — the create path scans the whole page, the editor path scans only the entries of the current author (ruling `A100`) — so all numbers of one decision come from one stream; a create therefore costs one resolve per existing entry of the page (accepted cost), a re-selection one resolve per own entry. The `block boundary space` between two `text fragment` values belongs to no fragment, so a range sitting on that code point touches its neighbours and shares nothing with them.
- Hidden entries and overlap (ruling `A22`): `visible` controls painting only, so the resolved range of a hidden entry participates in the overlap and duplicate checks exactly like a visible one. Turning a highlight off does not free its span for another note of the same author (`A22` still holds after `A93`); it never freed the span of a foreign author, because a foreign span was never a blocker.
- Stale entries and overlap (ruling `A24`): a `stale entry` has no resolved range, contributes no range to the checks, and can never block a create, so a new note may be created over text where an old note went stale. A resolution that yields no code point (an empty or inverted range) is read the same way. The stale entry itself stays listed and stays deletable.
- Duplicate entry (rulings `A23`, `A93`): an existing `own entry` is identical to a candidate when the resolved range is equal **and** the normalized comment is equal; the identical note of another author is not a duplicate of this reader's candidate and never refuses it. When both matches hold, `duplicate` is reported instead of `overlap`, because it is the more specific answer. The same range with a different comment is refused as `overlap`; the same comment at a different range is an ordinary second note unless the two ranges intersect. Comment equality compares the trimmed value, measured in code points.
- Anchoring: `anchor = { text, prefix, suffix, fragmentCount }` where `text` is the normalized selection text and `prefix`/`suffix` are the up-to-`contextWindow` characters before and after it, taken from the same normalized text stream; `fragmentCount` is a hint about how many DOM fragments the selection spanned, never an authority. Resolution happens in the normalized text stream: the two steps of "Anchor search order" give the code-point range, and the content layer maps that range back to DOM fragments (`content-overlay-ui.md`). Raw offsets are stored only as a hint and are never the authority. The window is taken at the boundaries of the **trimmed** span: the whitespace run a selection carries at either end, which "Normalized text" strips out of `text`, is not window content, so `prefix` and `suffix` are the context around the stored `text` and never around the raw selection (ruling `A27`). A window built on the untrimmed boundary would describe context the entry does not store, and a repeated sentence would anchor by the fallback step instead of by its context.
- Normalized text: normalization is a pure function of a string — every run of whitespace collapses into one U+0020, both ends are trimmed, and no non-whitespace character is reordered, added or removed. The whitespace set is **closed**, not categorical: it is exactly the set `WHITESPACE_RUN` matches in `src/core/text-normalize.ts`, namely U+0009 tab, U+000A line feed, U+000B vertical tab, U+000C form feed, U+000D carriage return, U+0020 space, U+00A0 no-break space, U+1680 Ogham space mark, the U+2000–U+200A run of Unicode space separators, U+2028 line separator, U+2029 paragraph separator, U+202F narrow no-break space, U+205F medium mathematical space, U+3000 ideographic space and U+FEFF byte-order mark; the 17 sampled forms pinned by `tests/core-text-normalize.spec.ts` are that set with the U+2000–U+200A run sampled at U+2000, U+2009 and U+200A. U+2028 and U+2029 are line and paragraph separators, not space separators, and both collapse. A code point outside the set is not whitespace and survives untouched: U+0085 (NEL) and U+200B (zero width space) are kept verbatim and are never trimmed, which is what makes the enumeration testable rather than open. It is idempotent (`normalize(normalize(x)) === normalize(x)`) and deterministic, and it is measured in Unicode code points, never in UTF-16 units, so `😀` is one character. The same function produces the normalized page text stream and the normalized selection text.
- Normalization ownership (ruling `A26`, closing residual risk 1 of `t1-06`): the content layer normalizes the selection at capture time; core never repairs it. `createEntryOnPage` refuses with `entry_invalid` and writes nothing when the given `text` differs from `anchor.text` or is not already normalized, so the highlight position and the stored span can never point at different strings. The refusal runs after the creation rules, so a full page still reports `page_limit`. A save never re-checks a stored record: Flow 7 keeps `text` and `anchor`, therefore a record stored before this rule keeps being editable.
- Anchor window: `prefix` and `suffix` are measured in Unicode code points, the default size is 40 and the caller may ask for another size. A selection at the very start or the very end of the stream gets a shorter window, and the anchor is never padded: a piece the page does not have would describe context that does not exist. The pieces are exact substrings of the stream they were built from, including the space that separates them from the selection, which is why searching the same stream finds them.
- Anchor options domain (ruling `A28`, same stance as `A26`): an option outside its domain refuses the anchor instead of being coerced. `contextWindow` must be a non-negative integer number of code points, where `0` is inside the domain and means "text only, no window"; `fragments` must be a non-negative integer, because the read guard rejects anything else. A negative, fractional, `NaN` or infinite value of either produces no anchor at all, and the caller treats that refusal as "do not create", never as a silent default — an anchor built from a coerced `0` would be indistinguishable from a caller that asked for no window context.
- Anchor search order: resolve in two steps — search `prefix + text + suffix` in the normalized text stream; when that yields nothing, search `text` alone; when neither is found, the anchor is stale. The first match in document order wins, so a repeated sentence is anchored deterministically and the same anchor on the same page text gives the same positions across reloads. There is no `anchor_ambiguous` code, because document order settles the choice (ruling `A24`). A hit is the half-open range `[start, end)` in code points of the same stream the anchor was built from.
- Normalized text stream (DOM side): the content layer turns a subtree into that one string (`src/content/anchor/text-stream.ts`), and both anchor directions use the result of that one function. The stream is the text-node content of the subtree in document order, with one `block boundary space` per boundary of the list below and nothing from an `excluded subtree`. Every piece is produced by the core `normalizeText` and every separator is a single U+0020, so the stream is normalized **by construction** (`isNormalizedText(stream.text)` is always true): it is trimmed at both ends, no separator is emitted at the start or the end of the stream, no two separators are adjacent, and between two neighboring contributing pieces there is exactly one U+0020. A whitespace-only text node contributes a separator and no text; a comment node contributes nothing. Rendered-but-hidden nodes are included in v1 (ruling `A1`): no `display` or `visibility` inspection happens in the stream.
- No raw-text equality (review finding `N2`): the stream is **not** `normalizeText` applied to the raw subtree text, and no such equality is claimed. `Node.textContent` concatenates adjacent elements with nothing between them, so the boundary spaces the walk contributes have no counterpart in the raw text: `<div><p>a</p>tail</div>` streams as `a tail`, while normalizing that subtree's `textContent` gives `atail`. The verifiable properties are the ones above — normalized by construction, one U+0020 per `A20` boundary, trimmed at both ends — and nothing else about the raw text.
- Block boundary (ruling `A20`, table cells added by ruling `A35`): `p`, `div`, `li`, `br`, `h1`–`h6`, `blockquote`, `tr`, `td`, `th`, `section`, `article`. Each boundary asks for one separator on entry and on exit; repeated requests collapse into the one U+0020 between two pieces, so two adjacent blocks contribute exactly one space and nested blocks contribute none of their own. That is what keeps two paragraphs from gluing into one word, what lets a selection across a `<br>` re-anchor, and what makes `<td>a</td><td>b</td>` stream as `a b` rather than `ab` (`A35`).
- Excluded subtree (ruling `A21`): `script`, `style`, `noscript`, `template`, `head`. Their text never enters the stream, not even as a separator. No other element is excluded in v1.
- Text fragment: the contract the content layer hands the painting stage — `{ node, start, end, streamStart, streamEnd }`. `streamStart` / `streamEnd` are the half-open **code point** offsets of that node's contribution inside the stream; `start` / `end` are the half-open **UTF-16** offsets inside `node.data`, the domain a DOM range needs. A fragment is never empty in either domain. Slicing the stream at a fragment's stream offsets reproduces `normalizeText(node.data)`. Fragments are ordered by document order, appear once per contributing text node, and every code point of the stream belongs to at most one fragment — the only stream code points outside any fragment are the single separator spaces between fragments.
- Anchor domains: an anchor range and a fragment's stream offsets are code points; a fragment's node-local offsets are UTF-16 units. An astral character is one code point and two units, and a whitespace run inside a node is one code point and several units, so the two numbers are never interchangeable. A conversion goes through `utf16IndexAt` / `codePointOffsetAt` or through the node's own code-point map; a `String.indexOf` result or a raw `nodeValue` offset never enters an anchor range unconverted.
- Anchor locate codes: the page-side locate of an anchor returns `{ ok: true, fragments }`, or `{ ok: false, code: 'anchor_not_found' }` when the anchor text is not in the current stream (the core code), or `{ ok: false, code: 'anchor_stale' }` when the text did resolve but the mapped range is no longer supported by the DOM: **any** text node it maps to is no longer inside the subtree, or any mapped node no longer accounts for exactly the code points the stream recorded, or the range covers only `block boundary space` code points and belongs to no text node. Both codes mean the same observable thing: no highlight, the entry stays listed and stays deletable. The locate throws nothing, mutates neither the anchor nor the page, and implements no second string search — the search belongs to `resolveAnchor`.
- Locate is all-or-nothing (ruling `A36`): a locate answers with every fragment of the resolved range or with none of them. One dead or disagreeing node invalidates the whole range, because painting the survivors would highlight part of a selection the user no longer has and would leave the other part unhighlighted with no signal. `{ ok: true, fragments }` therefore always means "every fragment of this range is a live descendant of the subtree the caller passed", and a caller never receives, stores or paints a filtered subset.
- Stream ownership (ruling `A29`, bounded by review finding `N4`): the normalized text stream belongs to the content layer, is rebuilt for every re-resolve (load, bfcache, SPA URL change, and each `locateAnchor` call), and is never cached. `src/core/` stores no position, and a cached stream would break the reload-stability property of "Anchor search order". Nothing under `src/content/anchor/` caches a stream, a node, an offset or a per-character decision either, so the module keeps no state that grows with the pages a content script visits: its only module-level data is the `A20` tag list, the `A21` tag list and the closed separator list, the three constant `Set`s derived from them (`BLOCK_TAGS`, `EXCLUDED_TAGS`, `WHITESPACE_CODE_POINT_SET` in `src/content/anchor/text-stream.ts`) and the two DOM node-type numbers the walk compares `nodeType` against; every one of them is a constant of fixed size, and no map, cache or counter there can grow with a page (review finding `N4`, wording fixed by `t3-04` remark 7). That separator set is the same enumeration as "Normalized text" above, and `tests/content-anchor-text-stream.spec.ts` compares it with `normalizeText` for every code point of the Basic Multilingual Plane, so the two views can never drift apart.
- Test-only DOM environment (ruling `A2`): `jsdom` is a `devDependencies` entry and the Vitest environment of the DOM anchor tests. It appears in no shipped module, in no manifest entry and in no built bundle, and a unit test fails if anything under `src/` references it or if it moves into `dependencies`.
- Staleness: if the anchor does not resolve, the entry produces no highlight but stays in the popup list and stays deletable. It is never auto-removed. The resolver reports the code `anchor_not_found`; the page-side locate reports `anchor_stale` for a resolved range that is not fully live (see "Anchor locate codes" and "Locate is all-or-nothing"); neither resolver throws, neither mutates the anchor, and neither removes or rewrites the entry — only an explicit user delete removes it.
- Ordering in the popup: creation order ascending.
- `visible`: boolean, `true` at creation and the default when the field is absent (PM ruling `A1`). It controls only whether the entry's highlight is painted on the page; it never affects entry identity, ordering, edit rights, the caps or the anchor. A hidden entry keeps its anchor and reappears when it is turned back on. Changing it is not an edit: the popup checkbox works for an entry of any author, and a visibility write never changes `updatedAt`, so it never moves the entry in the popup order. The field stays **per entry** after ruling `A108`: the popup groups a page by author and its checkbox is an aggregate over that author's entries, but the grouping is a read-side projection and no storage shape changes.
- Author aggregate write (ruling `A108`, task `t5-06`): `setVisibleForAuthor(port, { url, authorName, visible })` and `deleteEntriesOfAuthor(port, { url, authorName })` are the two named core operations behind the popup's group controls. They are built on the same primitives as the single-entry writes and obey the same rules — the `pageKey` is resolved through the stored index (`resolvePageKey(url, index) ?? pageKeyFromUrl(url)`, "Index write guard", finding `N5`), the author filter is `isSameAuthor` ("Identity", ruling `A99`, so a record authored `"Я "` belongs to the reader named `"Я"`), an unreadable record survives verbatim (ruling `A16`) because the guard cannot tell who wrote it, and every **other** author's record is kept by identity, never rewritten. The write is **one** page-slot write plus **exactly one** `pages:v1` update — the whole-list commit of "Index write policy" — never one commit per affected entry, because N commits rewrite the index N times and can leave a page half-applied. When the author owns the page's last readable entries, the slot key is removed before the index stops listing the page, exactly like a single-entry delete that empties a page. An author with **no** entry on that page is not an error: the call answers an empty result and performs **no** write of any kind, index included. The page argument is the page **address**, as in every other write of this module, so the caller never resolves a key of its own (ruling `A49` gives the popup only a tab address).
- Rename sweep (rulings `A173`, `A174`, task `t17-04`): when the settings name changes from `A` to `B` (`A !== B`), every stored note whose `authorName` is `A` is deleted from `chrome.storage.local` on **every page the page index lists** — core `deleteNotesOfAuthorOnAllPages` reads the index once and cleans each listed page with the shipped `deleteEntriesOfAuthor` call, so the write policy, the `A16` carry-through of unreadable records and the `A99` author identity are the ones that already shipped. Notes of other authors stay byte-identical, and a note whose name is the **new** name stays too (the rule does not assume there are none). The server is **not** called: this is a local deletion, and the server keeps what it has until the reader syncs. A page the sweep cannot clean (an unusable index, or a page whose slot refuses the write) keeps its notes and is reported with its machine code, so a partial deletion is never silent; the sweep continues with the remaining pages. The settings half — the order of the two writes, the warning before them, and the outcome sentence — is owned by `content-overlay-ui.md` -> "Options rename warning": the name is saved first and the notes are deleted second (`A174`), so a failed name save deletes nothing. The page's memory-held foreign notes are rebuilt on the next load, because the settings write is the storage change the page reacts to.
- Quota: writes are whole-list writes. If a write fails with a quota error, the entry is not created and the UI shows `Хранилище переполнено`.

## Edge Cases

- Selection inside the extension's own overlay (card, tooltip) must be ignored, not captured.
- Selection that spans several block elements and inline tags must work; a selection crossing `<table>` cells works because `td` and `th` are block boundaries (ruling `A35`), so the cells stream as separate words and the selection re-anchors instead of degrading to the innermost common container.
- Same text repeated on the page: the anchor's `prefix`/`suffix` disambiguates by the contextual search of "Anchor search order"; when the context no longer matches, or is empty, the search falls back to `text` alone and the first match in document order wins; the choice is stable across reloads because the search has no clock, no randomness and no iteration over object keys.
- Page text changed by the site (edit, re-render, comment section added) → the entry may go stale; it must not be silently dropped.
- Text that only moved between block elements (the site re-wraps the article): the `block boundary space` keeps the sentence spelled the same in the stream, so the anchor re-anchors onto the new nodes; text the site deleted reports `anchor_not_found`.
- A page that deleted **one** of the two nodes a remembered selection spaned goes `anchor_stale` as a whole (ruling `A36`): none of that entry is painted, and the entry stays listed and deletable.
- A create over the stored text of a `stale entry` is allowed, because a stale entry contributes no `resolved range` (ruling `A24`); both entries then exist, the stale one unhighlighted and deletable.
- A create over the range of a hidden entry is refused as an overlap (ruling `A22`); the checkbox is a painting control, not a lock on the span.
- A selection that crossed a `<br>`, an inline tag or a block boundary resolves to several fragments; a selection inside one text node resolves to exactly one.
- Reload, back/forward (bfcache), and SPA URL change must all re-resolve entries; a stale rendered highlight must be removed on URL change.
- Two browser tabs on the same page: a storage `onChanged` listener refreshes both; last write of the full list wins.
- Name changed in options: existing entries keep their old `authorName` and become read-only for the new name, and they stop blocking a create on their spans, because the overlap and duplicate rules are per author (`A93`).
- Two authors on one span: both entries exist, both are painted, and each is editable only by its own author (`A93`, `A25`).
- Duplicate selection with an empty comment is a no-op, not an entry.
- `chrome.storage.local` cleared by the user → the extension behaves as on a fresh install.
- `settings:v1` holds a value another writer produced (hand-edited, older build, wrong type) → `settings_malformed`, `name: ''`, no card on selection, the popup name-required message, and the next options save repairs the record.

## Acceptance Criteria

11. Unit tests in `tests/` cover rules 2, 3, 4, 6, 7, 8 and pass with no failing tests.
