# content-overlay-ui

## Purpose / Goal

Define everything the user sees and touches: the selection card, the page highlight, the hover tooltip, the in-place editor, and the extension popup contract for one page. The behavior here must be observable by a person loading `dist/` in Chrome.

## Scope

In scope: selection capture UI, highlight painting via the CSS Highlight API, tooltip, create/edit/delete widget, popup list and per-entry checkboxes, options page fields, SPA refresh, isolation from the host page.
Out of scope: storage layout, caps, authorship, anchoring rules (`inline-comment-model.md`), build tooling details.

## Flow / Sequence

1. User selects text on the page → once the selection has stopped moving for the `settle delay`, and once the `settings gate` answers with a usable name, the selection card opens at the `card placement` of that selection with an empty textarea, a live counter `0/256`, and buttons `Сохранить` / `Отмена`. A selection that resolves to no span at all opens nothing, and so does a `contained own selection`: a selection whose whole range lies inside the `resolved span` of one of the reader's own painted entries opens **no widget at all** (task `t5-03`, ruling `A103`). Every other selection opens the card, including one lying inside a `foreign entry`'s span.
2. User types and presses `Сохранить` → the span is re-derived against a freshly rebuilt `page text stream` (ruling `A29` in `inline-comment-model.md`), core validates, the entry is stored, the card closes, the highlight and its translucent frame appear.
3. User hovers a highlight → the page is asked for the caret at the pointer (`caret hit-test`); when that caret falls inside a `text fragment` of a **painted** entry, an opaque `tooltip` appears at the `card placement` of that entry's first `text fragment` box that has an area, showing the stored comment and the `ownership header`. Hovering painted text opens no selection card: hover is a caret lookup, and the `selectionchange` wiring of the card is untouched by it.
4. User clicks the `tooltip` → the `editor` of that entry opens over the entry's **own `resolved span` from the `paint pass`** (ruling `A104`): no `selection` is required, nothing is re-derived, the `textarea` is prefilled with the stored `comment`, the controls are `Сохранить` / `Отмена` / `Удалить`, and the widget is placed by the `card placement` rule against that entry's first `text fragment` that has a box. The opening dismisses the `tooltip` (ruling `A68`). A click on the `tooltip` of a **foreign** entry changes nothing on the page: no `editor`, no `selection card`, no message, and the `tooltip` stays (edit rights, `inline-comment-model.md`, ruling `A25`).
5. `Сохранить` updates the entry; `Отмена` or a click outside or `Esc` closes without changes; `Удалить` removes the entry and its highlight (shipped by `t3-03`).
6. The popup lists `entry rows` for the current page, the address of that page coming from the active tab rather than from the page itself (ruling `A49`). Pressing a checkbox writes that entry's `visibility flag` through core `setVisible`, and the popup re-reads its list from storage; the page repaints because of that storage write, not because the popup messaged it (ruling `A50`; the `storage watch` of `t4-03` is what ships that listener).
7. URL changes (SPA push/replace, back/forward, hash change) → the `url watch` of the page notices, and the `paint pass` runs again: it re-requests the entries of the new `pageKey`, resolves them against a freshly rebuilt `page text stream`, drops the `paint name`s of the page that is no longer shown, and paints the new set (`t4-03` AC1; rulings `A29`, `A39`, `A59`). An entry whose text the new document does not contain is unpainted and stays stored, listed and deletable; nothing is deleted by a navigation (`A24`, `A36`).
8. Options page (shipped by `t4-02`): opening the page reads the author name through the core settings read and shows it in the single `Имя` field with a `N/40` counter; a stored name the author rule refuses becomes the `first-run name`, stored through core, and a store that cannot be read shows an empty field with its message and writes nothing. `Сохранить` writes it through the core settings save. An empty trimmed value never reaches that save: the shipped gate for it is the **disabled `Сохранить` button** ("Counter and input cap"), and the reader-visible sentence for "there is no author" belongs to the popup and to the page card — «Укажите имя в настройках» — not to this field (review remark `R2`, closed by `t4-04`). `Имя обязательно` stays in the options map as the total-map answer to a core `name_required` refusal that no shipped control of this page can trigger ("Options message map").

## Rules / Semantics

- Highlight painting: CSS Highlight API (`CSS.highlights` + `::highlight(<paint name>)`), one named highlight per entry (ruling `A70`). Painting never mutates the host DOM and never adds elements to the page body other than the overlay host. The `::highlight()` rules live in the `paint stylesheet`, because a custom highlight has no element and no shadow tree of its own and `::highlight()` written inside a shadow root is ignored; `A41` variant 1 is what shipped, so the page gains **no** style element (ruling `A41`, task `t3-02` AC2). A browser without the Highlight API gets no painting and no DOM-spanning fallback (ruling `A38`); a browser without constructed stylesheets gets the painted spans in the browser's default colour and no frame.
- Author colour and `paint slot` (rulings `A94`, `A102`, task `t5-02`): the `paint stylesheet` still carries **one rule per `paint name`** (`A70`) and every name is still `inlinenotes-<entryId>`; what became per-author is the **declaration block** of that rule, taken from the `paint slot` of the entry's `authorName`. The mapping is a pure function of the stored name — the `fnv1a32` of `src/core/slot-key.ts` modulo `PAINT_PALETTE_SIZE` (**6**) — so the same author paints the same colour on every page and after every reload, and no entry id, page key, `visible` flag or per-page state enters it. The name is used **verbatim as stored**: core `author identity` (`isSameAuthor`, ruling `A99`) trims and core `createEntryOnPage` stores a trimmed name, so the one observable divergence is a hand-written record whose stored name differs by a space — core calls such records one author and the palette may colour them differently, which is another way of saying the colour answers no identity question. The palette lives in `src/content/paint/paint-palette.ts` (`PAINT_PALETTE`, `PAINT_SLOTS`, `paintSlotOf`), and `paint-plan.ts` is the only module that turns an `authorName` into a slot: the plan carries the slot with the `paint name`, and `paint-style.ts` writes the block of that slot. No other module copies a colour. The palette is fixed at **exactly six slots** and its slot 0 is the colour that shipped before this ruling, verbatim, so a page whose author occupies slot 0 does not change appearance at all. Two different author names may hash onto one slot and then share a colour: that collision is **accepted**, and no layer promises a unique colour per author. `src/core/` owns no rule about colour; the content layer imports the hash and owns the palette. A rule count that grew with the palette (one rule per slot) would break the per-entry teardown of ruling `A39`, so it is forbidden by the same sentence that fixes the name.
- Paint ownership and `paint teardown` (ruling `A39`): exactly one module writes `CSS.highlights` for the page. A repaint removes every extension-prefixed `paint name` and then paints the current set, and teardown removes **only** prefixed names and the extension's own sheet: `CSS.highlights` is document-global, so a highlight registered by the page or by another extension is not the extension's to remove.
- One `page text stream` per paint pass (rulings `A29`, `A37`): a pass rebuilds the stream once and resolves every entry of the page against that one stream, so twenty entries do not cost twenty walks, and no entry is resolved against a stream remembered from an earlier moment.
- A paint measurement that throws costs one entry (ruling `A66`): the entry loses its own highlight, is reported `measurement_failed`, and nothing else is cleared, written or hidden. A pass whose core read is untrustworthy (`storage_unavailable`, `layout_version`, `index_malformed`, `slot_malformed`, `url_unparsable`) paints nothing at all and runs a `paint teardown` first, because highlights from a state the page could not read are a lie; `entry_malformed` is not one of those codes, since one corrupt record does not make the good records of the page unpaintable.
- Text stream and fragments: before painting, the resolved anchor range is mapped onto `text fragment`s taken from a freshly rebuilt `page text stream`. The stream construction (block boundary space, excluded subtree), the fragment contract, the code-point versus UTF-16 domains and the locate codes `anchor_not_found` / `anchor_stale` are owned by `inline-comment-model.md` -> Rules / Semantics. Painting consumes the fragments it is given, never runs a text search of its own, and never paints a range that was not resolved against the current stream. The locate result is `all-or-nothing locate` (ruling `A36`): painting receives either every fragment of the resolved range or no fragment at all, so half of a remembered selection is never painted.
- `highlight frame`: `outline`-like translucent border around the highlighted box set (`text-decoration`/`outline` on the highlight pseudo-element), `rgba` color, no background fill of the author's own color choice — the reader picks no colour, and the `author palette` is the only source of one (ruling `A94`). Only the two properties the Highlight API honours vary per slot: `background-color` and `text-decoration`; nothing else about the frame differs between entries.
- Own entries and foreign entries are distinguished as **ownership** only in the `ownership header` (the reader's own word against the stored author name), and the reader's own notes carry **no extra page marker** (ruling `A94`). The `paint slot` colour says *which author*, never *whether this is mine*: it is a hash of a name, so a foreign note can wear the reader's own colour, and the colour is never read back as an ownership answer anywhere in the code. The tooltip, the editor and the popup keep deciding ownership through core `canEdit` alone. The header is decided by core `canEdit` over the author name the current pass read, so a settings state with no usable name makes every entry foreign, and `visible` is never part of the answer.
- Tooltip hit-testing: the `caret hit-test` compares the page caret with the node-local UTF-16 offsets the pass registered the ranges with, so the hit-test and the paint cannot disagree about what is painted. A caret exactly at a fragment's end answers that fragment, because a caret sits *between* characters and the last letter of a span would otherwise refuse the tooltip; an interior claim is checked before a boundary claim, so a boundary never steals an interior hit. A browser with neither caret API shows no tooltip — the same shape of degradation as a missing Highlight API (`A38`) — and nothing is faked from painted boxes. The hit-test searches only the entries of the last paint pass, which is what makes a hidden entry (ruling `A40`), a stale entry and an unresolvable entry unhoverable without any extra rule.
- Tooltip content is read from the entry record: the comment and the author name. It is never read off the page, because a custom highlight has no element to carry an attribute and painting is forbidden from writing one.
- Tooltip placement: the same `card placement` rule as the selection card (ruling `A30`, one function, no second geometry), against the entry's first `text fragment` box **with an area**, measured at hover time. A box measured by the paint pass is not reused for placement: a scroll moves every box in the document, and a tooltip placed against a stale box sits over text it does not describe. No fragment with an area means no tooltip (ruling `A67`), and a hover the page refuses to measure means no tooltip (ruling `A66`); in both cases the entry keeps whatever the last pass decided about it and stays listed and deletable in the popup.
- Tooltip lifetime: a `pointerdown` outside the overlay host, a page scroll and `Esc` each dismiss the tooltip; a `pointerdown` **on the tooltip** is the Flow 4 click — it asks the `editor` of that entry to open, or answers nothing for a `foreign entry` (ruling `A96`) — and it is neither a dismissal nor a cancel of any widget. This is the `close-on-scroll` logic of ruling `A32` reused, and the same separation as ruling `A68`: the tooltip and the selection card never hide the overlay host the other one is using, and neither owns the paint.
- Tooltip opacity: **1.0** from the first hover (the constant `TOOLTIP_OPACITY` in `src/content/overlay/tooltip-style.ts`, pinned by a test against this sentence; ruling `A96`, task `t5-03`). The two-state opacity the pre-`A96` design shipped — translucent on hover, opaque after a click — is gone, together with the class that click used to add: the stylesheet carries **one** opacity declaration and the controller chooses no class at all. The number lives in the stylesheet module, not in the controller, which owns no opacity decision. Only one editor instance may be open at a time (task `t3-03`).
- Overlay host: a single element with `position: fixed`, `z-index: 2147483000`, isolated styles (all rules namespaced under one host with a shadow root so page CSS cannot reach the widgets and widget CSS cannot leak out).
- Registered schemes: the content script is registered for `http://*/*` and `https://*/*` only (`src/manifest.json` -> `content_scripts[0].matches`); `file://`, `chrome://`, Web Store and PDF viewer pages are never injected into.
- Selection capture ignores selections inside the overlay host and inside `chrome://`, Web Store and PDF viewer pages (content script is not registered there).
- Permissions: `src/manifest.json` declares exactly `storage` and `tabs`, with no `host_permissions` and no `optional_permissions` (ruling `A49`, task `t4-01`). `storage` is the entry and settings store. `tabs` exists for one read: the popup asking `chrome.tabs.query({ active: true, currentWindow: true })` for the address of the tab it describes, shipped as `src/popup/active-tab.ts`, the only shipped module that names `chrome.tabs`. A popup document has no `window.location` of its own, so without that read the extension UI is blind on every page. The cost is the install-time warning "read your browsing history", which the user accepted for a personal-notes tool; the alternative (a service worker mapping `sender.tab.id` to a page key in `chrome.storage.session`) was rejected because it adds a moving part and makes the popup stop working on exactly the pages of the restricted-page edge case below. No later task widens this set without a ruling: `tests/toolchain-contract.spec.ts` pins the pair, and the popup's own injectable-scheme list (`INJECTABLE_SCHEMES` in `src/popup/page-entries-service.ts`) is pinned against `content_scripts[0].matches` so a new registered scheme cannot leave the popup answering from a stale list.
- Card placement (ruling `A30`): the card is one `position: fixed` box inside the shadow root, so its coordinates are viewport coordinates and it never scrolls with the page. It is placed **below** the box of the *first* `text fragment` of the selection **that has a box** when the whole card fits above the bottom `card gutter`, and **above** that fragment otherwise; its left edge and its top edge are clamped into the same 8 px gutter, so a selection at the very edge of the window still gets a reachable card; a card taller than the viewport is pinned to the top gutter rather than centered off-screen. The anchor box is measured with the same node-local UTF-16 offsets the paint uses, and the card box is measured after the mount, because the card stylesheet — not the placement code — decides its size.
- A `text fragment` box with no area takes no part in `card placement` (ruling `A65`). A fragment in a hidden or detached subtree contributes text to the `page text stream` (ruling `A1`) and measures as a zero box, and a zero box has no place next to it, so the placement walks to the next fragment of the span and stops at the first box that has an area. When **every** fragment of the span measures zero area there is no anchor point at all, and the card is placed by the same rule against the viewport itself — clamped into the 8 px `card gutter` — never at the corner of the overlay host and never at the coordinates of the zero box. The card still opens: a span that resolved is a span the user can write a note about.
- A painted entry whose fragments all measure zero area gets **no tooltip** (ruling `A67`): unlike the selection card, a tooltip is not placed against the viewport, because it describes a span the reader is pointing at and there is nothing to point at. The entry is not repaired, hidden or deleted by the hover.
- The page replaced a text node between the paint pass and a hover: the hover measurement throws, the tooltip does not open, and the pass is not re-run, cleared or rewritten (ruling `A66` applied to the hover path). The next repaint — a save, or the `url watch` of `t4-03` noticing a navigation — is what reconciles the page.
- Same-document navigation (`t4-03` AC1, rulings `A59`, `A29`, `A39`): the `url watch` of the page listens for `popstate`, `hashchange` and `visibilitychange`, and compares the page address every `url poll interval`, because a content script in the isolated world cannot see the page call `history.pushState`. Every trigger goes through one compare against the address the watch last saw, so a trigger that changed nothing is not work, and **a tick costs one address read and one string compare**: no DOM read, no layout, no range, no storage read, no allocation. A change asks the one `paint pass` to run again — the watches own no resolve, no `CSS.highlights` write and no storage read of their own — and that pass rebuilds the `page text stream` and re-resolves every anchor of the new `pageKey` against it (`A29`), tears down the `paint name`s of the page that is no longer shown (`A39`) and never deletes an entry: text that vanished is unpainted and stays stored, listed and deletable (`A24`, `A36`). `pagehide` / `pageshow` are deliberately not triggers: bfcache restore is the reload path, which re-runs the pass at load. Neither watch is ever torn down in a content script: this design has no unload step, so the teardown each watch returns exists for tests only, and the interval lives for the life of the document.
- Cross-tab repaint (`t4-03` AC2, ruling `A60`): the `storage watch` of the page subscribes to `chrome.storage.local` changes and asks for **one repaint** when the record names this page's entry slot or `settings:v1`, and does nothing at all otherwise — no core read, no paint call. `pages:v1` is not a signal: a write to any page updates the index, so treating it as one would make every open tab repaint for every note stored anywhere (ruling `A88`); the accepted consequence is that a write touching **only** `pages:v1` and no entry slot is not noticed, and no shipped write does that. One relevant record is one repaint: the listener keeps no queue, merges nothing, takes no lock and replays no change payload; the repaint re-reads the page through core, which is the only truth. What this does **not** change is the cross-tab read-modify-write limit `inline-comment-model.md` -> Edge Cases states: two tabs saving at the same moment are still last-writer-wins on the whole list.
- Settings name picked up without a reload (`t4-03` AC3, rulings `A31`, `A25`): the author name is read by every capture attempt (one fresh core read per attempt, ruling `A31`), so a name written in options opens the card that the missing name refused and makes an entry the reader now owns open its editor on the next `tooltip` click (ruling `A96`), with no help from the watches. What the `storage watch` adds is the painted page: the `ownership header` of a tooltip compares the stored `authorName` with the name **the last pass read**, so `settings:v1` is one of the watched keys and a name change repaints the page instead of leaving the previous author on screen. Neither path touches an open widget: an open card or editor keeps its draft, because a settings change is not a reason to discard what the reader typed.
- The pointer is over painted text while the page scrolled: the tooltip dismissed itself on the scroll (ruling `A32`) instead of chasing text that moved out from under a box measured earlier; hovering again re-measures and answers.
- Card lifetime (ruling `A32`): an open card is **closed, never repositioned**, when the page scrolls or when the selection moves to other boundary points; a scroll also cancels a capture that has not settled yet. After a close caused by a selection change, the settled selection opens a new card, which is Flow 1 happening again rather than a move of the old one. A `selectionchange` whose target is not the document answers nothing at all (the card's own textarea holds a selection while the user types), and a `pointerdown` inside the overlay host is not "outside": the card keeps its text. `Отмена`, `Esc` and a `pointerdown` outside the host discard the card and write nothing.
- Settings gate before the card (ruling `A31`): one capture attempt performs exactly one core `loadSettings` read, and "is there an author" is answered by core `validateAuthorName`, never by a truthiness test of the stored value. A stored name the author rule refuses — empty, or longer than the author cap — opens **no card at all** (not a card whose button can never be used), writes nothing, and shows no `refusal line`; the popup keeps its own «Укажите имя в настройках» message for the same state.
- The `contained own selection` (task `t5-03`, Flow 1, ruling `A103`): a page selection whose **both** boundary points lie inside the `resolved span` of one painted entry **of the current author** opens no widget at all. The question is answered from the output of the last `paint pass` — the node-local UTF-16 offsets the `paint name`s were registered with — so it cannot disagree with what is on the page, and no second resolve of the anchors is paid for. It is the only silence a selection can meet: a selection lying wholly inside a `foreign entry`'s span opens the `selection card` (creating there is legal since ruling `A93`), and so does a selection that only *crosses* one boundary of an own entry — the `overlap` rule answers at that write, which is where the reader is shown the sentence for it, and that rule answers only against entries of the current author (`A93`, `A99`, `A100`). A hidden (`A40`), stale (`A24`) or unmeasurable (`A66`) entry is absent from the `paint pass` output, so its words are never a `contained own selection` and a new note may be written over them.
- The `editor widget` is opened by a click on the `tooltip`, never by a page `selection` (ruling `A96`, task `t5-03`). Clicking the `tooltip` of an entry the author rule accepts as the reader's own opens the editor prefilled with the stored `comment`, anchored on that entry's own `resolved span` from the `paint pass` (ruling `A104`); clicking the `tooltip` of a `foreign entry` opens **nothing at all** — no textarea, no `Сохранить`, no `Удалить`, no message — because a foreign entry is read-only (`inline-comment-model.md` -> "Edit rights", ruling `A25`), and the `tooltip` simply stays where it was. A note of the reader's own on the same words is legal since ruling `A93`, and it is asked for by selecting those words, exactly like any other selection.
- Editor placement: the same `card placement` rule as the selection card (ruling `A30`), anchored on the first `text fragment` of the **entry** that has a box, and placed by the viewport half of the rule when the entry has none (ruling `A65` applied to the editor): an editor whose entry has no measurable box is still reachable, because it is not a description of a place the reader is pointing at. A placement measurement that **throws** opens no editor for that entry: the `tooltip` the reader pressed stays on screen, nothing is written, and the next `paint pass` is what reconciles the page — the ruling `A64` answer, applied to the `tooltip` click.
- Editor lifetime (rulings `A42`, `A43`): `Отмена`, `Esc` and a `pointerdown` outside the overlay host are **one** cancel path: the editor closes, its draft is discarded, and no write of any kind is attempted — neither a `set` of the page slot nor a `remove` of the entry. A page scroll closes it, exactly as with the card (ruling `A32`). A `selectionchange` does **not** close it, and that is the one deliberate difference from the card: the re-selection rule below is unreachable in a widget that closes the moment the reader drags a new selection.
- The editor keeps its range unless the reader re-selects (ruling `A45`): a save with no `re-selection` changes `comment` and `updatedAt` only, leaves the `anchor` exactly as it was, and asks no `overlap` question — the entry's own span is allowed to stand, which is what makes "save the comment of a note whose text the page moved" a comment edit and not a refusal. The comparison is the boundary points kept at the open moment against the page selection at the moment of the press, never a range resolved at the open moment against a range resolved now (`A37`); a selection inside the overlay host is not a selection of the page. Under ruling `A104` the open moment brings no selection of its own, so the boundary points kept are the ones the page happened to hold at the `tooltip` click, and a page that held none keeps no baseline: every selection made while the editor stands is then a `re-selection`, and the stale selection a click found on the page is not one. A `re-selection` is resolved against a `text stream` built at that moment and is the span the `overlap` check answers for, and that check **excludes the entry being edited** by removing it from the entry list the check scans — not by an `exceptId` parameter in core: an entry must never collide with itself, and "except the one you are editing" is not a question the core overlap check owns. The same list is filtered to the entries of the current author before the check (`A100`), so moving one's own note across a `foreign entry`'s words is allowed and moving it across a note of one's own is refused.
- Ruling `A78`: what a successful `re-selection` stores — **the editor owns a comment and a delete, nothing else**. A
  `re-selection` decides the `overlap` answer and changes no stored range: a save writes `comment` and `updatedAt`, and the
  `anchor` and `text` keep the span the note was created on; moving a note to other words is a delete plus a create. The
  alternative was a core write that carries an anchor — rejected: it is a `src/core/` change outside this slice and it
  re-opens the `text`/`anchor` consistency rule accepted in `t1-06` for a convenience the reader can get in two gestures.
  `docs/specs/inline-comment-model.md` -> "Overlap" and task `t3-03` AC5 ask only that a re-selection go through the
  overlap check with the edited entry excluded (and, since `A100`, with the entries of the current author only),
  and that is what is shipped and pinned
  (`tests/content-editor-controller.spec.ts` -> AC5). If the user overturns this ruling, the change is one core write, the
  sentence above, and that one test — nothing else in the content layer reads the difference. Ruling `A104` did not touch
  this ruling; it made the no-`re-selection` save the ordinary case again, because the `editor` a `tooltip` click opens
  carries no new span of its own, and the `re-selection` check itself is shipped exactly as `A78` accepted it.
- `Удалить` removes the entry, its `highlight` and its `tooltip` at once: no confirmation step and no undo in v1 (ruling `A44`), so the button itself is the only warning the action gets. The delete control is never rendered for an entry the reader did not write, and core applies no author check to a delete — the absence of the control **is** the rule (`A25`).
- Selection capture and save moments: a card opens only for a selection that resolves to a span, so an empty, collapsed or whitespace-only selection opens nothing and a user is never invited to type into a note that cannot exist. Saving re-derives everything from the boundaries the card kept, against a stream built at that moment (`A29`); nothing measured while opening is reused for the write. A span that no longer resolves is answered by the content layer with `selection_lost` and «Выделение больше не найдено на странице», nothing is sent to core, and the card stays open with its text — so `entry_invalid` stays a bug-level answer and is never the wording for "there was nothing to create".
- Refusal message map (rulings `A33`, `A47`): one module per UI layer maps every machine-readable code the create path can answer with to the Russian `refusal line`, and the map is total over the code union, so a call site can never invent wording and no code can be left without an answer (`src/content/text.ts` for the content layer). `duplicate` and `overlap` are two different refusals with two different sentences: the same span with the same comment already exists, while an intersecting span belongs to another note; collapsing them would hide which of the two the user has to change. The content-layer map:

- The card and the editor must be reachable by keyboard: `Esc` = cancel, `Ctrl/Cmd+Enter` = save, `Tab` cycles the controls in the order the shadow tree holds them: `textarea` → `Сохранить` → `Отмена`. The editor of `t3-03` keeps the same rule with one more control in the rendered order: `textarea` → `Сохранить` → `Отмена` → `Удалить`.
- `focus on open` (ruling `A74`, an `Assumption:` pending the user's word, applied as the least-risky default): opening the card takes **no** focus. The page keeps the element it had focused, nothing inside the overlay host is focused, and the reader reaches the card with `Tab` in the natural order of the shadow tree: no control carries a `tabindex` of its own, so the rendered order **is** the tab order and no control opts out of it. Rationale: the extension never intrudes on the host page (overlay AC2), and taking focus away from a page the reader did not ask to change is the same class of intrusion. Changing this is a behavior change with its own spec line, its own production edit and its own task. `tests/content-create-card-controller.spec.ts` pins the three shipped halves: the page's focused element survives `open()`, the three controls take focus in that rendered order with no `tabindex` anywhere in the shadow tree, and `Esc` / `Ctrl/Cmd+Enter` answer an open card (cancel with nothing written, save through the core create path). The editor of `t3-03` is under the same ruling for the same reason, and `tests/content-editor-controller.spec.ts` pins its half: opening the editor leaves the page's own button focused and focuses nothing inside the overlay host.
- Counter rules: `N/256`, turns warning color at ≥240, blocks input beyond 256 code points, `Сохранить` is disabled while the comment is empty after trim or over the cap.
- Popup contract (task `t4-01`, rulings `A25`, `A81`, `A82`, `A83`): title with the page host; one `entry row` per entry of the page in creation order (core `sortByCreatedAtAsc`), row content = `ownership header` + checkbox (checked = painted on the page) + `Удалить`. No comment text, no date, no filter of "mine only", and **no edit affordance on this surface at all**: no textarea, no `Сохранить`, and no comment write of `src/core/` is imported anywhere under `src/popup/`. `Удалить` is nevertheless rendered for every row, own or foreign, because core gates editing by authorship and never a delete (`inline-comment-model.md` -> "Edit rights", ruling `A25`). The popup reaches storage only through the one port adapter and writes only through the core entry API: it names no storage key, no storage API, no `chrome.storage` (the scan in `tests/toolchain-contract.spec.ts`), and it sends no message to the page (ruling `A50`).
- Popup ownership marker (ruling `A82`): a foreign row is marked by the `ownership header` — «Вы» for an entry core `canEdit` accepts against the name the popup's own settings read returned, otherwise the stored `authorName` verbatim — plus a row class: `OWN_ROW_CLASS` = `row row--own` and `FOREIGN_ROW_CLASS` = `row row--foreign` in `src/popup/page-entries-service.ts`. There is no «Не: …» sentence: naming one fact twice, in two layers, is what the grep anchors exist to prevent, and the shipped content layer already answers this question with one word. A settings state with no usable name makes every row foreign, and `visible` is never part of the answer.
- Popup checkbox (rulings `A1`, `A12`, `A50`): a press performs exactly one core `setVisible` for that entry id on that page and nothing else. It is not an edit, so a foreign entry can be hidden too; it changes `visible` and nothing else, so it moves no row — the order is creation order before and after, and no stamp moves — and it sends no message, so the page repaints from the storage write (the `storage watch`, `t4-03`) rather than from the popup. After a refused write the popup still re-reads the page: the list shows what the store says, and no new sentence is invented for a state this section does not name.
- Popup notices (rulings `A81`, `A83`): a state that is not a list is stated by a line **above** the list, and the list still renders below it, because entries that became invisible are entries the reader can no longer delete. `name_required` — «Укажите имя в настройках», the same sentence the page card shows for the same state — is a real `<button>`, keyboard reachable, that calls `chrome.runtime.openOptionsPage()` and writes nothing; no second "open settings" string exists. `page_not_injectable` — «На этой странице подсветка недоступна» — is one sentence for one state, whether the page is `file://`, `chrome://`, the Web Store, the PDF viewer, an address core refuses to turn into a `pageKey`, or a tab whose address the popup could not read. Both codes live in `src/popup/text.ts`, and the map is total over the code union. Empty list: `На этой странице нет записей`.
- Options author-name field (task `t4-02`, rulings `A54`, `A55`, `A56`): the page owns the author name and nothing else. It reads through core `loadSettings` and writes through core `saveSettings`; it names no storage key and no storage API, and its only storage surface is the one port adapter (`createChromeLocalStoragePort()` in `src/content/store/chrome-storage-port.ts`). The field never renders a stored value the author rule refuses: an absent, damaged or over-long record shows either the `first-run name` or an empty field plus its `options message line`, never the stored bytes. The wiring is `src/options/author-name-service.ts`; the component holds signals and nothing else, so the tests drive the service.
- First run (ruling `A54`): **every** stored name the author rule refuses is replaced by `generateAuthorName(rng)` and stored through `saveSettings` during the same page open. Which shapes that covers — the list of unusable stored values the generation runs over — is owned by `docs/specs/inline-comment-model.md` -> Rules / Semantics -> the "`authorName`" rule, and this spec deliberately does **not** restate that enumeration (review remark `R3`, closed by `t4-04`: one rule, one owner, so a future edit cannot desynchronize two copies). The reader is never asked to invent a name, and no other layer may generate one: `t4-02` is the only shipped caller of `saveSettings` and of `generateAuthorName` (same model rule), pinned by a grep test, not by this sentence. The one shape that is **not** generated over is a settings read that failed (`storage_unavailable`): writing a fresh identity into an area the page could not read would decide the author of every stored entry on a guess, so the field stays empty with its message and nothing is written.
- Counter and input cap (ruling `A55`): the counter under the field is `N/40`, the cap read from `MAX_AUTHOR_NAME_CODE_POINTS` and both numbers counted in Unicode code points, and the input refuses every code point past the cap, so 40 code points are accepted and the 41st is refused — the same boundary core enforces — while a name of 40 surrogate-pair emoji counts as 40 and is accepted. No `maxlength` attribute takes part in the guard: it counts UTF-16 units, so it would cut an astral name in half and let 41 emoji through. `Сохранить` is disabled while the value is empty after the trim or over the cap.
- Options save (ruling `A56`): `Сохранить` performs exactly one `saveSettings` call and nothing else — including when the value did not change, because that explicit save is what repairs a record another writer damaged — and a successful one shows `Имя сохранено`. A refused or failed save puts the name the store actually holds back into the field, because the core save leaves the stored value byte-identical; showing the typed value would print a name the reader does not have.
- Options message map (ruling `A33`, applied to this layer by `t4-02`): one module, `src/options/text.ts`, maps every code the settings read and write can answer with, plus the one confirmation, and the map is keyed by the code union of `src/options/author-name-service.ts` so the compiler checks its totality and no call site can invent wording. `name_required` is that single code for empty and over-cap alike (ruling `A11`), and the input refuses the over-cap case before a save is possible. **Reachability of this code on the options surface (review remark `R2`, closed by `t4-04`):** no shipped control of this page can produce it — `Сохранить` is disabled while the value is empty after the trim, and the input refuses every code point past the cap — so the row below is what the core save answers when some other caller hands it such a value, which is exactly what `tests/options-author-name.spec.ts` -> AC2 drives (the service, not the button). The reader who has no author sees «Укажите имя в настройках» of the popup and the page card, not this sentence. One wording per surface: the options map keeps `Имя обязательно` for this code where the card and the popup say `Укажите имя в настройках` for the same state, and `quota` reuses the sentence `inline-comment-model.md` fixes. A third variant of either state is forbidden.

- All strings are Russian and come from one constants module per UI layer.

## Edge Cases

- The anchor box is measured **before** the card is mounted, and a measurement that throws means the card does not open (ruling `A64`). `Range.setStart` / `setEnd` reject when the page shortened or replaced the selected text node during the `settle delay`, so the fragment list the capture built no longer fits the DOM. The capture then answers with nothing: no card is mounted without coordinates, the overlay host stays hidden, no read or write of an entry is attempted, and the next settled selection is a fresh capture. A card is never left on screen whose position the page could not report.
- Every `text fragment` of the resolved span measures zero area (a selection inside a `display: none` subtree, a collapsed text box, a node the page detached during the `settle delay`): the card opens and is placed by the viewport rule of ruling `A65`, inside the 8 px `card gutter`, not at the corner of the overlay host. A fragment whose box has an area later in the span is used instead, so a selection that starts in a hidden paragraph and ends in a visible one gets its card next to the visible words.
- Selection in a scrolled, sticky or transformed container: the card is positioned in viewport coordinates, and a page scroll **closes** it (ruling `A32`) instead of letting it float over text that has moved out from under it; a new selection is needed to open it again. (This line used to promise a reposition on scroll; ruling `A32` replaced that behavior in task `t3-01`, and `src/content/overlay/card-events.ts` implements the close.)
- Highlight of a range that spans several block elements must draw a frame around every fragment box, not one bounding rectangle.
- The site re-renders the article (virtual list, lazy load): a stale highlight disappears; the entry remains in the popup list.
- A locate that reports `anchor_not_found` or `anchor_stale` produces no highlight, no frame and no tooltip at all; the entry is still listed in the popup and still deletable (`inline-comment-model.md` -> Staleness).
- A tooltip near the viewport edge flips to the opposite side; it never covers the range it describes.
- Host page with an aggressive CSS reset or `all: unset`: shadow-root isolation must still render the widget correctly.
- Popup opened while the content script failed to inject (restricted page): the popup still lists the entries and states that the page cannot show highlights. Ruling `A81` fixed that sentence — `На этой странице подсветка недоступна` — and ruling `A49` is what makes the list possible there at all, because the popup asks the tab for its address instead of depending on a content script that never ran (`tests/popup-entry-list.spec.ts`).
- Options page opened over a record another writer damaged (`settings:v1` holding a string, a number, a non-string `name`, or a 41-code-point name): the field shows the `first-run name`, the record is rewritten as `{ name }`, and the reader can type their own name immediately. Entries made under the old name keep their stored `authorName` and become read-only (`inline-comment-model.md` -> Edge Cases); a damaged record is never shown in the field, because the field is where a name is chosen, not where bytes are inspected.
- Two tabs open on the same page: a change in one tab repaints the other tab's highlights through the `storage watch`, with no reload and no re-navigation, and updates the popup of that tab on reopen (the popup reads its list when it opens; `t4-03` AC2, ruling `A60`).
- A site that never changes the address (an infinite scroll that re-renders the same article): the `url watch` reports nothing, because its only question is whether the address moved. The entry that no longer resolves stays unpainted until the next repaint a real event causes — a save, a checkbox press, a storage change — and `inline-comment-model.md` -> Staleness is what keeps it listed and deletable in the meantime.
- A tab the reader left in the background: Chrome throttles its timers, so the `url watch` re-checks the address on `visibilitychange` as well, and a navigation the page made while the tab was hidden is caught when the reader returns rather than up to one `url poll interval` later.
- Entry hidden via its checkbox: no highlight, no frame, no tooltip, and therefore nothing on the page to click for the `editor` (ruling `A96` retired the selection route back to it); the entry stays stored, listed and deletable in the popup, and its editor is reachable again as soon as its checkbox paints it.
- A `tooltip` click the page refuses to measure — the entry left the document between the `paint pass` and the click: no `editor` opens, the `tooltip` the reader pressed stays where it was, and nothing is written; there is no fallback to the `selection card`, because a click is not a selection (ruling `A64`, applied to Flow 4).
- A `tooltip` click on a `foreign entry`: the `tooltip` stays and nothing else on the page changes. The reader is told nothing, because a foreign note is not the reader's business (`A25`), and no `selection card` opens in its place.
- Two authors whose names land on one `paint slot`: both paint in that slot's colour, the two rules are identical apart from their `::highlight()` name, and nothing else changes — no re-mapping, no search for a free slot, no warning. The collision is a property of hashing into six slots and is accepted with the ruling that fixed the palette size (`A94`, `A102`).
- Own and foreign ranges overlap on the page: both `paint name`s are registered and the CSS Highlight API blends them; the extension invents no z-order, no priority and no per-author registry, and the `overlap` refusal of rulings `A93`/`A100` stays a rule of `src/core/` asked at the write moment, never a paint-time one.

## Page-boundary throws

The content layer is the only layer that calls code it does not own. Any of those calls
can answer with a throw instead of a value, and a throw that escapes the content script is
an unhandled rejection on a page that has no idea the extension exists. This section is
the **single place** that enumerates those paths (task `t3-05`, ruling `A75`): a new
`catch` under `src/content/` either appears in the table below with a test or is named
there with the reason it has none, and a reviewer reads this table before accepting a
content-layer diff.

Three rules:

- **Where the guard sits.** At the content call site that knows what the answer means for
  that flow — never in `src/core/`, and never inside the module that made the call.
  `src/content/capture/selection-span.ts` has no `catch` of its own and keeps propagating
  the `InvalidAccessError` that `Range.intersectsNode` throws once the boundary node the
  card kept and the fragments of a freshly built `page text stream` no longer share a
  root; `src/content/create/create-note.ts` and the card controller are the call sites
  that decide what that throw means. Core keeps throwing its own errors (ruling `A75`).
- **What the answer is.** An outcome the layer already has: an existing refusal code, an
  existing skip reason, or "nothing happens". No `catch` in the content layer introduces a
  new code, a new Russian string or a new state, and no `catch` writes to storage.
- **Which promises must not reject.** A UI promise whose caller has no rejection handler:
  `PagePainter.refresh()`, run as `void painter.refresh()` by `src/content/main.ts` at load
  and again on the create handover, and `CreateCardController.capture()`, run as
  `void controller.capture()` by `src/content/overlay/card-events.ts`. Both are non-rejecting by
  contract, and the contract is a test claim, not a comment claim: a `refresh()` that
  throws at any stage answers with an empty pass, a `paint teardown` of the `paint name`s
  it had registered, no write, and the code of the stage that failed, and the entries stay
  stored, listed and deletable (rulings `A40`, `A66`). The card's save path keeps **no**
  `catch`: `createNote` answers every page-boundary state as a `CreateNoteResult`, so the
  card's busy / `refusal line` machine has exactly one input. The editor's save and delete
  paths keep the same shape for the same reason: `EditorController.submit()` and
  `EditorController.remove()` have no `catch`, because `saveEntryComment` guards the page
  calls it makes and answers them as an `EditNoteResult`. The defect this section
  closes was the opposite shape: the throw escaped `submit`, the card stayed `busy`,
  `Сохранить` rendered disabled and no line appeared at all. The two watches of `t4-03`
  (`url-change-watch.ts`, `storage-change-watch.ts`) ship **no** `catch` of their own and
  add no new page-boundary call: the only foreign thing either one does is read
  `window.location.href` or read the keys of a change record it was handed, and the call
  they make is the non-rejecting `PagePainter.refresh()`, run as `void painter.refresh()`
  exactly as at load.

## Acceptance Criteria

1. On an arbitrary article page, selecting text shows the card with a `0/256` counter and `Сохранить` disabled until at least one non-space character is typed.
2. After save, the selection is painted with a translucent frame and no page element was added or modified in the DOM other than the single overlay host.
3. Hovering the painted text shows an **opaque** tooltip with the comment and the author name, read from the entry record; it is opaque from the first hover and no click changes any opacity (`t5-03`; ruling `A96`). Clicking the tooltip of one's **own** entry opens the `editor` of that entry, and clicking the tooltip of a **foreign** entry changes nothing on the page (`t3-03`, ruling `A25`).
4. In the editor, `Сохранить` persists the change, `Отмена`, `Esc` and a click outside discard it, `Удалить` removes the entry and its paint (`t3-03`; rulings `A42`, `A43`, `A44`). The editor a `tooltip` click opens is anchored on that entry's **own `resolved span` from the `paint pass`**: it requires no page selection, re-derives no range, and a save with no `re-selection` changes `comment` and `updatedAt` only (`t5-03`, rulings `A104`, `A78`).
5. A selection lying wholly inside the `resolved span` of one's **own** painted entry opens **nothing at all** — no create card, no editor (`t5-03`, ruling `A103`). A selection lying inside a `foreign entry`'s span opens the create card, and a selection that only *crosses* one boundary of one's own entry opens the create card, where the `overlap` rule answers at the write (`t3-03`, `t5-01`; rulings `A45`, `A93`, `A99`, `A100`).
6. A selection overlapping an entry **of the current author** shows `Выделение пересекается с существующей записью` and creates nothing; a selection overlapping only an entry **of another author** creates its note (`t5-01`; rulings `A93`, `A99`, `A100`).
7. The popup shows one row per entry with only the author name and a checkbox; unchecking removes the highlight immediately, checking restores it.
8. Navigating inside an SPA to a different article changes the popup list and the painted highlights without a manual reload.
9. Typing beyond 256 code points is impossible; the counter never exceeds `256/256`.
10. With no usable name in options — empty, or longer than the author cap — no card opens at all, nothing is written, and the popup shows `Укажите имя в настройках`.
11. A host page with a global CSS reset still renders the card and the tooltip with correct fonts and spacing.
12. A page scroll, a selection that moved to other words, `Отмена`, `Esc` and a pointer press outside the overlay host each close the card and write nothing, and the card is never moved to follow a selection or a scroll (`A32`).
13. A selection near the bottom or the side edge of the window gets its card above or inside the edge, and the card never comes closer to the viewport edge than the 8 px `card gutter` (`A30`).
14. Saving the same comment over the same span a second time shows `Такая заметка на этом выделении уже есть`, an intersecting selection shows `Выделение пересекается с существующей записью`, and in both cases the card stays open with the typed text (`A47`).
15. Painting and hovering add no element to the host page and no `<style>` to it: the only page-level element is the overlay host, and the `::highlight()` rules are an adopted stylesheet (`A41` variant 1). A repaint removes only extension-prefixed `paint name`s (`A39`), one pass walks the page once for every entry (`A29`), and a measurement that throws costs one entry and nothing else (`A66`).
16. An entry that is hidden (`A40`), stale or unresolvable is neither painted nor hovered, and stays listed and deletable in the popup. An entry with no fragment box has no tooltip (`A67`). The tooltip and the selection card never hide each other's host and never open each other (`A68`); the click of a `tooltip` opens the `editor`, which is a different handover and dismisses the `tooltip` instead of hiding a host (`A96`).
17. Opening the selection card moves no focus: the element the page had focused is still the document's active element, and nothing inside the overlay host is focused (`A74`). `Tab` then reaches `textarea`, then `Сохранить`, then `Отмена`, in that order, with no `tabindex` on any control; `Esc` closes the card and writes nothing, and `Ctrl/Cmd+Enter` performs the save (`t3-02b` AC1).
18. The options page shows the author name core read, and over a damaged or empty record it shows the `first-run name` — 8 lowercase base36 characters, read back equal to what the core settings read returns afterwards — or, when the store cannot be read at all, an empty field plus `Хранилище недоступно` and no write. The stored value is never shown in the field. `Сохранить` writes exactly `{ name: <trimmed value> }` under the settings key through core and performs no other write (`t4-02` AC1-AC3).
19. The counter reads `N/40` in Unicode code points: 40 code points are accepted and saved, the 41st code point is refused at the input, a name of 40 surrogate-pair emoji counts as 40 and saves, and `Сохранить` is disabled while the value is empty after the trim (`t4-02` AC4).
20. The options page reaches storage only through the one port adapter: no file under `src/options/` names `chrome.storage` or a storage key, `saveSettings` has exactly one shipped caller, and `generateAuthorName` has exactly one shipped call site (`t4-02` AC5; pinned by greps in `tests/toolchain-contract.spec.ts`).
21. A page that takes the selected text away between the card opening and `Сохранить` gets «Выделение больше не найдено на странице» in the `refusal line`, has nothing written, and keeps a usable card: `Сохранить` is enabled, the draft is still in the `textarea`, and `Отмена` and `Esc` still close the card and write nothing (`t3-05` AC1). No content-layer promise whose caller has no rejection handler rejects: `PagePainter.refresh()` and `CreateCardController.capture()` resolve in every `page-boundary throw` state, and a paint pass that throws paints nothing, tears down the `paint name`s it had registered, writes nothing, and leaves every entry of the page stored, listed and deletable (`t3-05` AC2; rulings `A40`, `A66`, `A75`). Every `catch` shipped under `src/content/` is named in the "Page-boundary throws" enumeration above, and that enumeration is one section (`t3-05` AC3; pinned by `tests/content-throw-boundaries.spec.ts`).
22. The popup lists the current page's entries through core only: the address comes from the active tab (`tabs` permission, ruling `A49`), the rows are in creation order, and a row is the `ownership header` + a checkbox + `Удалить`, with no edit affordance anywhere on this surface (rulings `A82`, `A25`). Unchecking writes `visible: false` through core and the row keeps its position and its stamps, checking writes `true`, and a foreign row is hidden and deleted exactly like an own one (rulings `A1`, `A12`, `A50`). The «Укажите имя в настройках» line renders above a list that still renders and opens the options page while writing nothing (ruling `A83`); a page the content script is not registered for gets «На этой странице подсветка недоступна» and keeps its list (ruling `A81`); an empty page gets `На этой странице нет записей`; deleting the last row leaves that empty state at once (`t4-01` AC1-AC5; pinned by `tests/popup-entry-list.spec.ts` and by the popup scan plus the exact `storage` + `tabs` pin in `tests/toolchain-contract.spec.ts`). That render contract is pinned there as an order-and-nesting fact, not as a wording grep: both notice branches stand before `class="rows"` in document order, the empty-state paragraph is gated only by the empty check, and the list block, its checkbox and `Удалить` sit inside no notice and no ownership condition (`t4-03` CF1).
23. A page that changed under the notes tells the truth about itself with no reload and no re-navigation of the tab (`t4-03` AC1-AC3): a same-document address change — caught by `popstate`, `hashchange`, `visibilitychange` or the `url poll interval` of ruling `A59`, whose shipped constant a test asserts against the Terms row — re-resolves every entry of the new `pageKey` against a freshly rebuilt `page text stream`, so text that moved is painted again and text that vanished is not painted, is not deleted, and is still listed and deletable, while the `paint name`s of the previous page key are gone (`A29`, `A39`, `A24`, `A36`); a trigger that changed no address is no work, and a tick reads no DOM. A storage change to this page's slot or to `settings:v1` repaints within one repaint (`A60`), a change to another page's slot or to `pages:v1` is no work at all, and one record is one repaint with no queue, merge or lock. A name written in options reaches the loaded page: the ownership comparison follows it after the repaint the settings key causes, the card the missing name refused opens on the next capture, and the entry that became the reader's own opens its editor on the next `tooltip` click (`A31`, `A25`, `A96`). Pinned by `tests/content-spa-refresh.spec.ts`, `tests/content-cross-tab-refresh.spec.ts`, `tests/content-chrome-storage-port.spec.ts` and the core key predicate in `tests/core-storage-keys.spec.ts`.
24. The page surface answers the `overlap` rule per author at both of its two entry points (`t5-01`; rulings `A93`, `A99`, `A100`): a `create card` save whose span intersects or duplicates only a `foreign entry` is **stored**, so the page then holds two entries on the same words and each keeps its own editor rights (`A25`); a save that intersects an entry of the current author still shows `Выделение пересекается с существующей записью` and writes nothing; a `re-selection` in the open `editor widget` that lands on a `foreign entry`'s span saves the comment, and one that lands on another entry of the current author is refused with that same sentence and writes nothing. The refusal sentences themselves are unchanged (`A47`), and the author comparison is the one `author identity` rule of `inline-comment-model.md` -> "Identity", so no content-layer file compares `authorName` by hand. Pinned by `tests/content-create-card-controller.spec.ts` and `tests/content-editor-controller.spec.ts`.
25. The colour of a `highlight` follows its author (`t5-02`; rulings `A94`, `A102`): two entries of one author on one page carry the same `paint slot` and therefore the same declarations, two entries of different authors carry the slots of their own names, and the mapping is pinned as literal slot values for named inputs so a palette edit cannot reshuffle every author silently. The `author palette` has **exactly six** slots and slot 0 is the pre-`A94` colour verbatim, so a page whose author occupies slot 0 does not change appearance at all — an author landing on another slot sees their notes recoloured, which is the point of the rule. The `paint stylesheet` still carries exactly one `::highlight()` rule per painted entry, every rule named `inlinenotes-<entryId>`, and the rule count does not grow with the palette. A hidden (`A40`) or stale (`A24`) entry still paints nothing, `paint teardown` still removes only extension-prefixed names (`A39`), and overlapping ranges of different authors are **both** registered — the blend is accepted and the `overlap` rule itself is untouched (`A93`, `A99`, `A100`). No new Russian UI string appears, and `src/content/text.ts`, the popup and the options page are untouched. Pinned by `tests/content-paint-palette.spec.ts`, `tests/content-paint-plan.spec.ts`, `tests/content-paint-style.spec.ts` and `tests/content-page-painter.spec.ts`.
